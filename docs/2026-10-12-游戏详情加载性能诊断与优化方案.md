# 游戏详情加载性能诊断与优化方案

日期：2026-10-12。状态：第一批优化已实施并上线，结果见《2026-10-12-详情性能优化发布记录.md》。以下诊断数字保留实施前基线；第二、三批留待后续按收益安排。

## 结论

有明确且较大的优化空间。当前详情接口复用了全库目录加载逻辑，打开一款游戏也会读取所有产品、所有渠道记录、解析全部图集并检查大量图片文件。应优先改为按游戏 UUID 定向查询，再完善前端即时反馈和图集布局。

同一服务器、同一数据库的只读实验中，现有目录加载约 2,018 毫秒；按游戏查询的原型包含详情序列化仅需 15～21 毫秒。三款渠道记录最多的游戏，公开详情字段与原逻辑完全一致。该实验支持方案方向，但不是已上线收益，也不代表浏览器完整加载可以达到 20 毫秒。

### 服务端只读诊断

数据库规模：5,744 款产品、9,328 条渠道记录；原始 JSON 合计约 96.79 MiB。图片资产表有 7,106 条图标记录和 26,954 条截图记录。

不启用性能分析器时，现有 `_load_catalog()` 一次耗时 2,018.46 毫秒。额外启用分析器的单次调用中：

- 对 9,328 条渠道记录逐条提取图集，累计约 1.11 秒，其中 JSON 解析约 0.84 秒。
- 执行 39,681 次文件存在性检查，累计约 0.87 秒。
- 分析器下总耗时约 2.99 秒；分析器本身有额外开销，以上累计时间存在包含关系，不能相加作为耗时分解。

只读原型保持相同的事件、图集和介绍选择函数，只改变数据读取范围：

| 产品 | 关联渠道记录数 | 定向读取及序列化，三次 | 公开详情一致性 |
| --- | ---: | --- | --- |
| 王者万象棋 | 22 | 20.55 / 18.37 / 18.26 毫秒 | 完全一致 |
| 英雄冒险家 | 20 | 15.67 / 15.07 / 15.11 毫秒 | 完全一致 |
| 蜀山幻想志 | 19 | 17.56 / 17.05 / 17.01 毫秒 | 完全一致 |

此对比不包含登录态、关注查询、HTTP 编码、网络传输、浏览器渲染或冷文件缓存；原型在基线加载之后执行，数据已有预热。它不是全量兼容性测试。查询计划已确认成员查询使用 `(game_id, source_row_id)` 主键索引及来源记录主键；UUID 和媒体 URL 也已有相应索引，无需先增加重复索引。

## 瓶颈及影响

1. `webapp.py:1473` 的 UUID 详情接口先执行 `_load_catalog()`，再从全库结果中筛选一款游戏；旧整数 ID 接口同样如此。
2. `webapp.py:319` 加载全部渠道记录的 `raw_json` 并解析，还遍历全库图片资产检查文件。此前流式处理降低了内存峰值，但并没有消除每次请求的全库工作量。
3. `webapp.py:313` 使用进程内 `_CATALOG_LOAD_LOCK`。列表、统计、日历、详情共用此路径，同进程请求会等待其他目录加载结束。排队程度尚未实测，不据此宣称固定额外延迟。
4. `app.js:193` 打开抽屉后只有“正在读取产品档案”，必须等详情接口返回才显示已有的游戏名称、图标等信息。缺少详情请求错误恢复和过期响应校验，切换游戏时可能被较早的请求覆盖。
5. `app.js:273` 等待所有图集图片取得宽高比例，最迟 3.5 秒后才调整布局。它不会阻塞介绍文本插入，但可能造成图集晚调整和页面跳动。
6. 抽测的静态资源有 ETag，未返回显式 Cache-Control；这不等于完全没有浏览器缓存，但可以进一步明确缓存策略。

## 建议实施顺序

### 第一批：定向详情查询 + 前端即时反馈

**后端定向查询，优先级最高，改动成本中等。**

- 新增单游戏读取函数：先解析 UUID 合并链，再查一条产品记录及其关联成员。
- 仅解析该游戏的来源原始数据；仅查询该游戏相关的图标、截图缓存记录，并检查相关文件。
- 继续使用现有事件去重、介绍选择、图集来源排序和五图上限，保持接口结构。
- 同步覆盖旧整数 ID 接口，保留 ID/UUID 合并重定向、异常链处理和关注时间语义。
- 单游戏查询不经过全库目录锁；不直接删除仍保护全库加载的锁，以免恢复全库并发内存峰值。
- 第一批不依赖详情缓存即可获得主要收益，避免缓存掩盖查询问题。

**前端即时反馈与请求管理，改动成本低至中等。**

- 保留列表中已有产品数据，点击后先展示名称、图标、厂商和简介，详情区域显示占位内容，接口返回后补全。
- 渠道视图中的来源数、事件轨迹、图集等可能只是当前渠道范围，先保持占位，避免当作完整产品信息展示。
- 为详情请求增加错误提示、重试、请求取消和请求序号校验；关闭抽屉或切换游戏后，旧响应不得覆盖当前内容。
- 可增加有数量上限、短有效期的浏览器内存缓存。公共资料与用户关注状态分离；关注变更、登录和退出时更新或失效用户状态。
- 大规模悬停预取暂缓，先消除后端全库加载，再评估是否有必要增加预取。

### 第二批：减少其他页面请求对详情的干扰

**列表、统计、日历使用轻量读取路径，改动成本中等至高。**

- 列表和计数查询不加载全量原始 JSON、完整介绍和全库媒体缓存；仅为最终当前页补齐必要的展示资源。
- 统计与日历直接使用所需的事件、日期和产品字段。
- 可引入有上限的短时公共缓存，采集入库、目录重建和媒体更新后失效；每日日期切换也必须纳入缓存键或失效条件。
- 这部分必须保留“事件先取最新版本再筛日期”、产品/渠道双口径和关注筛选语义，建议独立实施与验收。
- 前端首次启动时优先启动列表请求，避免统计和日历完成前完全不加载列表。

### 第三批：图集布局和静态资源缓存

**减少图片晚调整和重复下载，改动成本中等。**

- 媒体缓存时记录宽高，API 返回图片尺寸或宽高比，前端提前预留空间；历史媒体缺失尺寸时有稳定的默认比例，不在请求现场全库读取图片补尺寸。
- 首屏可见图片优先加载，其余按需加载；不再等待全部图片才能确定整个图集布局。
- 配置静态资源缓存。只有确认文件内容不可变、URL 随内容更新时才使用长期 `immutable`；否则采用版本化 URL 或较短缓存加校验。
- JSON/JS/CSS 压缩可作为后续补充，但详情返回体积很小，收益低于消除全库加载。

## 验收建议

以下为拟定目标，不是本次已经达到的线上指标：

- 点击后 100 毫秒内出现已有基本资料和加载状态。
- 普通网络、低并发条件下，详情接口 P95 争取控制在 500 毫秒内；部署后按实际网络基线校准。
- 覆盖不同渠道、成员数量和媒体缓存状态的至少 20 款游戏，多轮记录响应时间；区分首轮与重复请求，不用几次抽样推算可靠 P95。
- 在受控低并发下同时执行详情与列表/日历请求，确认详情不再等待全库目录锁。
- 比对介绍来源、事件日期、渠道顺序、图集优先级和本地/远程降级结果；覆盖旧 ID、合并 UUID、无效游戏、缺图与关注状态。
- 浏览器检查连续点击 A/B、请求失败、关闭后晚返回、重新登录和图片慢加载，确保不串页、不永久停留在加载状态。
